# 从这个项目开始学习 Go Web 开发

先运行项目，再沿着“浏览器 → HTTP → 状态 → JSON 文件”读代码。目标是能独立解释、修改并验证一个完整操作，而不是记住全部语法。

## 1. 先认目录，再认启动入口

在 Ubuntu 的 `~/projects/go-linux-study-todolist` 执行 `pwd` 和 `ls`。Windows 对应的展示目录是 `D:\Codex_project\go-linux-study-todolist`。

| 文件或目录 | 负责什么 |
| --- | --- |
| `go.mod` | 模块名与 Go 语言版本 |
| `main.go` | 数据类型、校验、文件存储、HTTP 路由、服务启动 |
| `main_test.go` | 后端与存储测试 |
| `curriculum.json` | 12 周课程，属于只读计划 |
| `web/` | 浏览器加载的 HTML、CSS 和 JavaScript |
| `data/state.json` | 运行时生成的个人进度，不提交到 Git |
| `.gitignore` | 排除个人数据和编译文件 |

从 `main()` 往下读：读取环境变量 → 检查回环地址 → 读取课程 → 载入状态 → 启动 HTTP 服务。遇到不熟的函数，先写一句“输入是什么，输出是什么”，再看细节。

```bash
go run .
```

在浏览器打开 `http://127.0.0.1:8787`。浏览器负责显示界面，终端里的 Go 进程负责处理请求和保存文件。`Ctrl+C` 结束进程后，浏览器不会再收到 API 响应。

验收：能找到上述文件，解释 `main()` 的流程，并知道数据保存在哪个目录。

## 2. 区分课程模型与个人状态

`Plan → Week → Task` 表示固定课程。任务包含 ID、标题、分类、预计分钟、说明和资源链接。`curriculum.json` 通过 `//go:embed` 进入程序，所以修改课程后要重新运行或编译。

`State` 表示个人进度。它只保存各任务的勾选、笔记和实际分钟，并额外保存开始日期和自定义任务。任务 ID 把课程与进度关联起来；不要随意改已使用的课程任务 ID，否则旧进度无法对应。

以下是一个合法状态的形状，日期可换成你的开始日期：

```json
{
  "version": 1,
  "revision": 0,
  "startDate": "2026-10-12",
  "tasks": {
    "w01-t01": {
      "done": false,
      "notes": "已确认 Go 版本，还需练习路径。",
      "actualMinutes": 30
    }
  },
  "customTasks": [
    {
      "id": "custom-review-path",
      "title": "再练一次绝对路径",
      "category": "Linux",
      "minutes": 20,
      "weekId": "week-01",
      "description": "从其他目录进入项目，并解释 pwd 输出。"
    }
  ],
  "updatedAt": ""
}
```

`version` 表示数据格式版本；`revision` 表示保存次数，用来发现不同窗口的冲突；`updatedAt` 由服务端成功保存时填写。任务未出现在 `tasks` 中时，前端把它当作未完成、空笔记、实际 0 分钟。自定义 ID 使用 `custom-` 前缀且不能重复。

分类固定为 `Go`、`Linux`、`Git`、`数据库`、`项目`、`算法`、`求职`、`计算机基础`。`validateState` 会检查日期、ID、分类、长度和分钟范围。理解这些检查如何保护文件格式，比只看页面输入框更重要。

验收：能解释为什么预计分钟在课程里、实际分钟在状态里，以及为什么请求仍需服务端校验。

## 3. 先理解两个 GET 接口

保持服务运行，另开终端：

```bash
curl -i http://127.0.0.1:8787/api/plan
curl -i http://127.0.0.1:8787/api/state
```

| 接口 | 返回内容 |
| --- | --- |
| `GET /api/plan` | `{ "weeks": [...] }`，课程内容 |
| `GET /api/state` | 当前完整个人状态 |
| `PUT /api/state` | 校验并保存完整状态，返回新状态 |

查看响应首行的 `200 OK`、`Content-Type: application/json` 和下面的 JSON。再到 `handler()` 找到相应路由，沿着 `jsonResponse()` 看结构体如何编码成 HTTP 响应。

验收：能用 curl 获取课程和状态，指出状态码、响应头与响应体的位置。

## 4. 再理解 PUT 和修订号

PUT 会发送完整状态，而非只发送某一个任务。每次保存必须带上刚读取的 `revision`。服务端成功保存后将它加一，并返回更新后的完整状态。

在练习数据中测试即可。先通过页面导出当前进度。Ubuntu 示例：

```bash
curl -s http://127.0.0.1:8787/api/state > /tmp/study-state.json
nano /tmp/study-state.json
curl -i -X PUT http://127.0.0.1:8787/api/state \
  -H 'Content-Type: application/json' \
  --data-binary @/tmp/study-state.json
```

编辑时只修改某个任务的 `done`、`notes` 或 `actualMinutes`，保留其余字段和当前 `revision`。响应中的修订号会加一。原封不动再次发送旧文件会得到 `409 Conflict`，因为文件里仍是旧修订号。这是乐观并发检查：先让客户端操作，在保存时判断期间是否发生了其他保存。

收到 `409` 后，应重新 GET 当前状态，再合并自己尚未保存的修改；直接拿旧快照覆盖新状态会丢掉另一窗口的内容。输入错误一般得到 `400`，Content-Type 不正确得到 `415`，保存失败得到 `500`。服务端返回错误时不会把失败的快照当成新状态。

验收：成功保存一次，并用旧修订号触发一次 `409`；解释为什么前端必须接受服务器返回的 revision。

## 5. 跟到 JSON 持久化

在 `newStore()` 看初次默认状态和已有文件读取。在 `Store.update()` 看加锁、修订检查、校验、保存和内存更新的顺序。在 `saveFile()` 看建目录、编码 JSON、写临时文件、同步并替换原文件。

这里有两个不同的问题：`Mutex` 避免同一 Go 进程里多个写请求同时修改存储；`revision` 避免两个浏览器窗口先后发送旧快照时互相覆盖。临时文件替换减少写到一半留下不完整 JSON 的风险。只有文件保存成功，程序才更新内存中的状态并返回成功。

默认 `data/` 相对启动工作目录。需要固定位置时设置 `STUDY_DATA_DIR`。不要在服务运行时直接编辑 `state.json`，因为内存快照与磁盘内容可能不一致。查看文件可以使用：

```bash
cat data/state.json
```

验收：勾选一个任务并写笔记，停止再重启服务后仍然存在；能从日志确认保存路径。

## 6. 看前端怎样发请求与显示状态

在 `web/` 中找 `fetch` 和 `render` 相关代码，用浏览器开发者工具的 Network 面板观察请求：刷新页面会获取计划与状态，修改进度会保存状态。

前端的主要工作是：将课程和状态组合显示 → 接收用户修改 → 请求保存 → 使用服务器返回的新状态。它也处理筛选、周次、日期、导入导出和自定义任务。错误提示属于用户流程的一部分，保存失败时不能显示“已保存”。

课程和笔记是文字内容，插入页面时应使用安全的文本方式，避免把笔记当作 HTML 执行。打开两个窗口，先在 A 保存，再在 B 操作，观察冲突提示与刷新后的记录。

验收：能在 Network 面板找到一次 PUT，请求里的 `revision` 与响应里的新值，并指出一个显示错误的处理分支。

## 7. 运行测试，再做一次人工验证

```bash
go test ./...
go test -race ./...
go vet ./...
```

先读 `main_test.go`：找一个成功用例、一个非法状态用例、一个并发冲突用例和一个文件保存失败用例。测试用临时目录，不应改动个人 `data/state.json`。竞态检测需平台支持和 C 编译器；环境不满足时先修好工具链，再完成该项验证。

自动检查通过后，在页面验证勾选、笔记、分钟、自定义任务、日期和 JSON 备份。重启后再看一次，确认界面与文件都正确。修改后运行相关检查；不必为每一处文字或样式改动重复全部测试。

验收：能说明一条测试如何发现真实问题，完成导出→修改进度→导入备份→重启验证。

## 8. 用 Git 提交并推送自己的改动

先查看改动，再提交，不要把笔记、密码或二进制一起加入仓库：

```bash
git status
git diff
git add main.go main_test.go web README.md docs curriculum.json .gitignore go.mod
git commit -m "Explain and verify my study tool change"
git push
```

`git push` 需要已经配置远程仓库与认证。没有远程时，先创建自己的 GitHub 仓库，再按 GitHub 提供的命令连接，不要随意填写别人的地址。推送后在网页检查提交；在新目录 clone 并按 README 运行，确认文档真的够用。

验收：一次提交只包含相关内容，能读 diff 解释自己的修改；公开仓库中没有个人学习数据。

## 9. 下一次独立改动：给自定义任务增加优先级

这项功能还未实现，适合作为你的第一次完整扩展。先写下预期行为：自定义任务可选低、中、高优先级，默认中；可按优先级排序；旧备份导入后仍能使用。

按以下顺序逐步做，每一步都先验证再继续：

1. 在 `CustomTask` 增加优先级字段，定义允许的值和默认值；想清楚旧文件缺字段时如何兼容，不要立刻更改 `version` 规避问题。
2. 在 `validateState` 检查非法值，在新建与导入流程中补默认值；保证未知字段或无效值不会悄悄存入文件。
3. 前端增加选择框和排序方式，明确相同优先级的顺序；确认保存后能读取相同值。
4. 用测试覆盖合法、非法、旧状态兼容、保存后重启；在两个窗口观察修订号冲突仍能处理。
5. 更新 README 和开发说明，提交并推送；写 5 句复盘，说明自己遇到的问题与依据。

验收：从 UI 输入到 API 校验再到文件保存都能解释；旧备份可以导入，新的优先级在重启后保留。这样的一次独立改动，比只运行现成项目更能说明你学会了什么。
